Translation - Kimi K2: A Deep Evaluation Beyond the Chat Interface

A comprehensive evaluation of Kimi K2's Agentic AI capabilities through real-world programming and research tasks, revealing both its strengths as an execution-focused model and the challenges of ecosystem integration.

Recently, whenever a new large language model is released, we can always see a wave of evaluation reports. But there’s an interesting phenomenon: the vast majority of evaluations are invariably confined to an environment we’re most familiar with—the chat interface.

This is actually a fundamental limitation. In 2025, when Agentic AI is all the rage, evaluating a model designed for Agentic capabilities within a chat interface is like using whiteboard coding to interview a development director. The feedback you get has almost no relation to its core capabilities.

Kimi K2, released by Moonshot AI, has from the very beginning clearly positioned Agentic capabilities—that is, the ability for intelligent agents to autonomously use tools to complete tasks—in an extremely important position. This is a very rare choice in the entire field. For example, DeepSeek R1 only added tool-calling functionality quite some time after its release, and many platforms like ollama still don’t fully support it today. Kimi K2 takes the opposite approach, developing Agentic capabilities as a core competency, which in itself is worth evaluating with a paradigm that’s closer to its design goals.

Why We Must Go Beyond Chat Interfaces: The Evaluation Dilemma of Agentic AI#

But before we proceed, we must first clarify the premise of our discussion: What exactly is the core of Agentic AI? It has two inseparable core elements:

  1. Autonomous Decision-Making and Feedback Loops: This is the true manifestation of intelligence. An Agentic model doesn’t just passively answer questions; it needs to be able to autonomously break down a large goal into step-by-step action plans. More critically, it observes the results of its own actions—such as whether a file was successfully written or code compilation failed—and then adjusts based on this feedback to decide what to do next. This is a continuous perception-thinking-action loop.

  2. Tool Invocation and Environment Interaction: These are the “hands and feet” connecting the model’s brain to the real world. The model itself cannot directly operate your computer; it needs to achieve this through tool invocation. These tools can be operating system-level functions, such as reading and writing files or executing code, or they can be functions that connect to the external world, such as web searches or retrieving video content.

Understanding these two points helps us see why simply chatting with AI completely fails to evaluate its Agentic capabilities.

First, the chat format, in most cases, doesn’t require invoking any tools at all, so naturally it cannot evaluate this capability. Its interaction is purely text generation. You ask, it answers, rather than you speak, it acts. Here we are in 2025, still using the same approach to evaluate ChatGPT to assess a model designed for Agentic purposes—this itself represents a disconnect.

Second, chat interfaces severely limit the complexity of problems. A true Agentic task requires continuous context and environmental awareness. Tasks within chat interfaces are often isolated with extremely short contexts. They cannot construct the kind of feedback loop mentioned earlier, where the results of a previous compilation failure determine the next round of modification strategies.

Therefore, the only way to evaluate the true capabilities of an Agentic model is to place it in a real environment where it can get its hands dirty. I spent some time conducting a more systematic analysis of Kimi K2 that’s closer to its design intentions, by directly writing code to call its API.

Programming Test: The Friction Between High-Level Intelligence and Execution#

In the Agentic world, programming is a classic comprehensive task. To evaluate a model’s true capabilities in programming tasks, we similarly cannot adopt the mode of copying and pasting code back and forth in chat interfaces. That question-and-answer approach fragments what should be a continuous, complex engineering task into countless discrete, scattered Q&As. This way of using AI is like applying telegraph thinking to sending WeChat messages: compressing what should be an immersive collaborative information space into a small box where context is frequently lost, then making do with manual补全 to keep things running—both inefficient and counterproductive.

This is precisely why the emergence of Agentic programming environments like Cursor or Claude Code represents revolutionary progress.

Their core value lies in building a real arena where AI models can truly stretch their legs. In this environment, the model is no longer just a chat partner, but transforms into a copilot equipped with a series of tools like reading and writing files, executing code. It can finally work like a real human developer in actual codebases, building that crucial feedback loop and truly participating in stateful, continuous task flows.

Therefore, to evaluate K2’s real capabilities, the first thing I did was integrate it into the powerful Agentic programming environment of Claude Code (specific methods at the end of the article), and had it develop a chicken-crossing-the-road game from scratch. The first version it produced was quite playable, and after two or three iterations, it was basically bug-free. However, the entire development process was far from smooth—it could even be described as bumpy. I had a clear impression: there exists an obvious gap between the model’s high-level intelligence and low-level tool execution.

On one hand, Kimi K2’s intelligence is first-rate. Its understanding of tasks, decomposition of game logic, and the quality of final code generation are all at industry-leading levels. It can understand my intentions well and write genuinely effective programs or perform effective debugging. This is a very smart “brain.”

But on the other hand, when this brain needs to interact with the real file system through its “hands and feet” (i.e., tool calls), systematic friction begins to appear. For example, in the Claude Code environment, it seems to have its own preferences for handling file paths, which causes it to repeatedly fail when attempting to read and write files. Those “cannot find string to replace” errors in the logs are not random bugs, but rather a consistent pattern throughout. This gives me the feeling that the model and tools are like speaking the same language with different accents, often leading to misunderstandings.

More seriously, when it’s handling particularly complex tasks, it sometimes just stops mid-sentence. This sudden interruption of the reasoning process is fatal for an Agentic system. An intelligent agent that cannot reliably complete tasks is unreliable. So what might be the root causes of these problems? I speculate there are mainly two levels of reasons:

First is systematic tool mismatch. Claude Code is an environment Anthropic built specifically for their own Claude models. Its tool instruction formats, internal prompt templates, and expectations for model outputs have all been fine-tuned to perfectly match Claude models’ temperament and personality (universal Agentic programming tools like Cursor or Trae also need individual adaptation for each model. The main reason we don’t use Cursor/Trae here is that they don’t have the convenient integration method like Claude Code Router). Kimi K2 is like a potentially highly skilled actor with a different accent who’s suddenly placed in a script written for another lead actor. It can understand the general meaning of the lines, but consistently deviates on certain key intonations, rhythms, and subtexts. The file path handling issues mentioned earlier are likely manifestations of this accent mismatch.

Second, a more specific technical reason might be context window limitations. Agentic programming environments are very context-intensive, requiring the entire conversation history, system prompts, and code from multiple currently open files to be stuffed into the model’s memory. Claude Code’s natively adapted Claude 4 model has a 200K context window, while Kimi K2’s currently available API is 128K. When the entire task context exceeds this length, the model may exhibit unpredictable behavior, such as the sudden reasoning interruptions I observed. This might not be Kimi forgetting what to say, but rather its workbench being full and unable to process new information. Of course, this is just one possibility; another possibility is that, similar to Gemini 2.5 Pro, Kimi K2’s training process didn’t perfectly handle long-chain tool processing, which would require further in-depth investigation.

Therefore, my hypothesis is that the bumpy development process is not due to deficiencies in Kimi K2’s intelligence level. It exposes a deeper problem: the contradiction between a potentially top-tier AI brain and hands and feet that haven’t been fully adapted to it. This results in a less-than-ideal user experience. This is a problem worth considering for all teams dedicated to Agentic AI development.

Information Research: The Execution Resilience of Agentic Models#

My second test was open-ended information research. This is a scenario that better tests a model’s autonomous planning and iterative execution capabilities.

It was precisely in this test that Kimi K2 demonstrated its enormous value as a system component. I discovered it has a very precious characteristic that I call task execution resilience. When facing a complex research topic, it will very naturally generate large quantities of diverse keywords, then tirelessly conduct multiple rounds of iterative searches. It has a strong bias for action, while many other models, when facing this type of open task, quickly start to slack off, preferring to use their existing knowledge rather than actively explore. For example, GPT-4o, Gemini, Deepseek, and Qwen all have similar problems. Even when the system prompt repeatedly emphasizes “please absolutely must search with multiple keywords,” they’ll just casually search for one or two rounds or even be too lazy to search at all and directly start answering.

Of course, it also has a significant shortcoming. Possibly because K2 is not a reasoning model, while it’s very good at collecting and compiling information and can provide you with an extremely detailed list of materials, it’s not good at extracting profound, high-level insights from these materials. It’s more like a top-tier information gatherer rather than an analyst. This point is actually very similar to o3—o3 can also tirelessly invoke multiple rounds of searches, but in the end often just generates a simple running list. Moreover, this issue of thinking depth is very difficult to change. It’s like telling an intern multiple times (through prompts) that reports need strategic height—they still can’t write VP-level reports for you. This is a limitation of the model’s inherent capabilities.

But this can already provide tremendous value. A model with strong execution resilience is the foundation for building complex Agentic systems. Because in a system, the most valuable quality is not occasional flashes of brilliance, but predictable, reliable execution. A component that can always faithfully complete instructions is far more valuable than one that’s brilliant but makes its own decisions. You can build more diverse and reliable automated workflows around it. I used to always use o3 to complete such tasks, but due to o3’s cost, I was always hesitant to extend this approach to more complex tasks. Now Kimi K2’s emergence has given me a low-cost but quite comparable quality option.

This directly spawned a very efficient workflow. I now use Kimi K2 as the frontend of a research system, leveraging its strong execution resilience and long-text capabilities to perform carpet-bombing information gathering on any topic I want to research. Then, I hand the extremely information-rich context that Kimi has organized directly to a reasoning model that excels at deep analysis, such as Gemini 2.5 Pro as the backend, letting it complete the final step of analysis and insight extraction. This two-stage combination works surprisingly well. Not only does the final output quality far exceed any single model, but due to Kimi’s cost-effectiveness, the entire process costs significantly less compared to o3. This gives me a clear view of Kimi K2’s precise positioning in a complex Agentic system: a tireless, exceptionally capable doer.

Moreover, I’ve found that Kimi’s shortcoming in reasoning ability can also be compensated through workflow design. I’ll have it first play the role of an architect, generating a detailed and clear step-by-step plan for a complex task. This plan itself is equivalent to us manually injecting a thinking component for it, externalizing and structuring the thinking process. Then, I’ll have it play the role of a scheduler, strictly and step-by-step calling various tools to execute the plan it just created. This achieves a decoupling of planning and execution in a multi-agent system. As a scheduler, it can call search engines, invoke code interpreters, and even call another model that excels at analysis (such as Gemini 2.5 Pro) to complete a particular step in the plan that requires deep thinking.

Some Final Thoughts#

So, after this round of testing, I feel that Kimi K2’s advantages and deficiencies are both quite apparent. Its strategic bet on the Agentic direction is a rather visionary move. But between its powerful potential and current reliable execution capability, there indeed still exists a gap.

Kimi K2’s most precious asset is its intelligent brain. But the value of this core asset is being consumed by unstable tool calls and ecosystem friction. If we want it to fully realize its potential, I think there are two things that may be unavoidable:

First is proactively solving the last-mile problems of the ecosystem. Expecting the community to spontaneously create perfect adaptations for Kimi would be a very lengthy process. A more proactive approach would be to directly engage in deep collaboration with one or two mainstream Agentic programming tools, such as Cursor or Trae, for targeted fine-tuning, or even releasing official, deeply adapted open-source toolchains. There’s only one goal: upgrading the usability of Agentic capabilities to the reliability that developers can trust. This is a key step in building a true moat.

Second is treating reasoning stability as a core engineering metric. The problem of tool calls stopping midway must be located and solved at its root. Because this problem directly determines whether Kimi K2 will ultimately become an interesting toy or a productivity tool that developers can rely on. The upper limit of an intelligent agent is often determined by its most unstable component.

Overall, Kimi K2 gives me the feeling of unpolished rough jade. Its core material—the model’s intelligence—is excellent, showing us the enormous possibilities of Agentic AI’s future. Its task completion resilience and cost-effectiveness have already made it the default frontend of my information research system. But the challenges it currently faces are not a lack of intelligence, but rather the friction between engineering and ecosystem integration. What position it will ultimately occupy in AI history will largely depend on the determination and speed of bridging this gap.
